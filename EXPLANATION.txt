================================================================================
  CVX_OPTIONS: TWO-OPTIMIZER ARCHITECTURE
  Last updated: 2026-02-22
================================================================================

This project implements two portfolio optimizers for an equity + options + cash
portfolio. Both share the same data pipeline, forecasting engine, and option
pricing mechanics; they differ in how risk is measured and how allocation
decisions are made.

  Optimizer          Risk metric       Problem type    Key advantage
  ─────────────────  ────────────────  ──────────────  ──────────────────────
  Markowitz++        Variance (Σ)      QCQP (SOCP)    Familiar, fast, vol cap
  Scenario CVaR      CVaR from MC      LP (R-U)        Tail-aware, no Σ needed


================================================================================
1. SHARED FORECASTING ENGINE
================================================================================

Both optimizers are driven by the same chain of data → forecasts → scenarios.
The distinction is what each optimizer *consumes* from that chain.


A) Option Chain Loading and Filtering
--------------------------------------
1. Load calls_{date}.parquet and puts_{date}.parquet from option_chains/.
2. Apply strict filters: min_mid ≥ $0.10, max bid-ask spread ≤ 35%.
3. If fewer than MIN_BL_STRIKES (25) survive, relax: min_mid ≥ $0.02,
   spread ≤ 80%.
4. Select the expiry with the best DTE/strike coverage (target 35–75 DTE).

Q: Do we need more strikes?
   BL density needs ≥ 25 clean OTM strikes spanning ±10% of spot for the
   IV spline to produce a well-conditioned second derivative. With Alpaca
   data we typically get 30–50 after filtering, which is adequate. If you
   add very illiquid names or far-dated expiries with wide spreads, the
   relaxed filters kick in. The system is self-healing: if BL fails, the
   lognormal fallback uses only ATM IV (1 strike is enough). More strikes
   improve the tails of the BL density but don't change the ATM region much.


B) Breeden-Litzenberger (BL) Risk-Neutral Density
---------------------------------------------------
1. Extract OTM implied vols: calls for K > spot, puts for K < spot.
2. Fit a 4th-degree smoothing spline σ(K) weighted toward ATM.
3. Evaluate smooth BS call prices C(K) on a 500-point grid.
4. Compute q(K) = e^{rT} · d²C/dK² — the risk-neutral PDF of S_T.
5. Validate: mean(S_T) within tolerance of spot; strikes span spot; density
   not degenerate (>20% non-zero mass).
6. If BL passes: sample S_T via inverse-CDF.
7. If BL fails: use lognormal with ATM IV (extracted via Newton-Raphson BS
   inversion from nearest ATM mid-price).

Fallback rate with Alpaca data: ~30–60% BL success (vs. ~0% with yfinance).


C) Physical-Measure Scenario Generation
-----------------------------------------
BL gives a risk-neutral (Q) density. For portfolio optimization we need the
physical (P) density — which includes the equity risk premium.

1. Estimate physical drift: μ_p = r + equity_premium.
   - If EQUITY_PREMIUM_ANNUAL is set: use that constant.
   - Else: estimate from rolling 252-day log-return mean (floor: r + 2%).
2. Tilt BL samples from Q → P via Esscher transform:
     weights_i = exp(θ · log(S_i/spot)), θ = (μ_p - r) / σ²_atm.
   Or, if BL failed: sample from LogNormal(μ_p, σ_atm) directly.
3. Result: n_samples draws of S_{rebalance} under physical measure.


D) Option Returns (Horizon Repricing with Dynamic IV)
------------------------------------------------------
For each scenario draw S_next:

  Equity:     r_eq = S_next / spot - 1

  Call:       C₁ = BS_Call(S_next, K_atm, r, T_remain, σ_call(S_next))
              r_call = C₁ / C₀ - 1

  Put spread: Long ATM put at K_atm, short OTM put at K_lower.
              P₁_long  = BS_Put(S_next, K_atm, r, T_remain, σ_put(S_next))
              P₁_short = BS_Put(S_next, K_lower, r, T_remain, σ_put(S_next))
              r_put_spread = (P₁_long - P₁_short) / spread_entry - 1

  Cash:       r_cash = e^{r·T_rebal} - 1

Dynamic IV (skew model):
  When S_next < spot, IV gets a volatility bump proportional to the down move:
    down = max(0, (spot - S_next) / spot)
    excess = max(0, down - SKEW_THRESHOLD)
    σ_call(S) = σ_call_0 + 0.25 · SKEW_BETA · excess
    σ_put(S)  = σ_put_0  + SKEW_BETA · excess

  SKEW_BETA = 2.5 means a 5% drop adds +0.10 to put IV. This captures the
  empirical leverage effect and makes put protection more expensive exactly
  when you need it (no free lunch). Default SKEW_THRESHOLD = 0.01 ignores
  the first 1% of any move.

Entry prices use ask (buy) side; exit prices subtract half the bid-ask spread.

Result: R ∈ ℝ^{N×4} for single-asset [eq, call, put_spread, cash],
        or ℝ^{N×(3K+1)} for K underlyings.


================================================================================
2. MARKOWITZ++ OPTIMIZER
================================================================================

Problem formulation
--------------------
  maximize    μ_wc' w  -  (γ/2) · w' Σ_wc w  -  τ · ‖w - w_prev‖₁

  subject to:
    w ≥ 0                                    (long-only)
    w ≤ w_upper                              (per-asset caps)
    Σ w = 1                                  (fully invested)
    w_cash ≥ min_cash                        (cash floor)
    ‖w - w_prev‖₁ ≤ max_turnover            (turnover cap)
    ‖L' w‖₂ ≤ max_port_vol                  (hard portfolio vol cap, SOCP)
    w_call_i + w_put_i ≤ max_option_weight   (per-sleeve option cap)

Where:
  μ_wc = μ − ρ         worst-case return (DeMiguel et al.)
  Σ_wc = Σ + κ·diag(Σ) worst-case covariance
  L     = cholesky(Σ_wc + εI)

Default parameters:
  γ = 5.0       risk aversion
  ρ = 0.01      return uncertainty per asset (cash = 0)
  κ = 0.10      covariance diagonal boost
  max_port_vol = 0.12  per-period portfolio std cap


How Markowitz builds μ and Σ
------------------------------
μ (expected returns):
  - Rolling mean of past ROLLING_WINDOW (26) periods of realized returns.
  - Shrunk 50% toward the risk-free rate: μ_t = 0.5·μ_roll + 0.5·r_cash.
  - Cold-start (< 8 periods): μ = [0.005, 0, 0, r_cash].

Σ (covariance):
  - **RND component**: sample covariance of horizon-repriced Monte Carlo returns
    from the option chain (held-contract semantics, sticky-strike IV).
  - **IEWMA component**: CM-IEWMA predictor (3 half-life pairs) updated with
    realized returns each period.
  - **Dynamic blend (CM-IEWMA)**:
      * Per-period weight `a_rnd_t ∈ [0, 1]` depends on BL quality and IEWMA
        expert-entropy (confidence).
      * Σ_t = (1 - a_rnd_t)·Σ_iewma_cm + a_rnd_t·Σ_rnd.

This gives Markowitz a forward-looking (option-implied) Σ blended with a
distributionally-robust historical Σ (CM-IEWMA), instead of a fixed blend.


================================================================================
3. SCENARIO CVaR OPTIMIZER
================================================================================

Problem formulation
--------------------
The scenario optimizer now targets **relative tail risk vs a benchmark**, with an
additional absolute CVaR term to avoid pathological “short-vol” portfolios:

  - Benchmark:
      * Single-asset: SPY equity column.
      * Multi-asset  (3K+1): equal-weight of all equity sleeves.
  - Relative return per scenario:  `rel_rets = port_rets - bench`.
  - Losses:
      * Relative:  `loss_rel = -rel_rets`.
      * Absolute:  `loss_abs = -port_rets`.

Objective:
  maximize    μ_phys' w
             - λ_rel · CVaR_α(loss_rel)
             - λ_abs · CVaR_α(loss_abs)
             - τ · ‖w - w_prev‖₁
             - ε·‖w‖²

subject to:
  - w ≥ 0                                    (long-only)
  - w ≤ w_upper                              (per-asset caps)
  - Σ w = 1                                  (fully invested)
  - w_cash ≥ min_cash                        (cash floor)
  - ‖w - w_prev‖₁ ≤ max_turnover            (turnover cap)
  - w_call_i + w_put_i ≤ max_option_weight   (per-sleeve option cap)
  - **Tracking constraint**:
        mean(rel_rets) ≥ track_eps
    which caps long-run benchmark underperformance from hedging drag.

CVaR is linearized via Rockafellar–Uryasev separately for relative and absolute loss:
  CVaR_α(loss) = min_t [ t + (1 / N(1-α)) · Σᵢ max(lossᵢ - t, 0) ]

  Auxiliary variables: t ∈ ℝ (VaR threshold), uᵢ ≥ 0 (excess losses).
  Constraints:   uᵢ ≥ lossᵢ - t,  uᵢ ≥ 0
  CVaR =         t + Σuᵢ / (N(1-α))

This remains a linear program: fast and exact, but now explicitly controls
**relative** and **absolute** tail risk, and enforces a soft tracking floor.

Default parameters:
  α = 0.95              tail probability (worst 5%)
  λ_rel = 0.05          CVaR penalty on relative loss (port − bench)
  λ_abs = 0.30          CVaR penalty on absolute loss (−port)
  track_eps ≈ −0.0005   per-period tracking floor (small underperformance allowed)
  ε = 1e-4              quadratic regularization for stability


How Scenario CVaR builds its inputs
-------------------------------------
μ_phys (expected returns under P):
  - Equity: mean of equity column in scenario matrix (physical drift).
  - Options: set to 0 (fairly priced under Q; CVaR + tracking constraint drive allocation).
  - Cash: exp(r · T_rebal) - 1.

R (scenario matrix):
  - Shape: (N, 4) for single-asset or (N, 3K+1) for K underlyings.
  - Each row is one Monte Carlo path of [r_eq, r_call, r_put_spread, r_cash].
  - Generated by the shared forecasting engine (section 1D above).

The key insight: the scenario optimizer never collapses information to (μ, Σ).
It sees the full joint distribution of returns — including skewness, kurtosis,
and tail dependence — which is critical for options.


================================================================================
4. DYNAMIC HEDGE SIZING
================================================================================

Both optimizers use the same dynamic hedge sizing system to determine how much
put protection to buy each period. This replaces the old binary "tactical puts"
on/off switch with a continuous signal.

Three signals are combined:

  Signal         Weight   Inputs                  Interpretation
  ─────────────  ──────   ──────────────────────  ──────────────────────
  Tail risk      50%      CVaR of equity column   Higher tail → more hedge
  IV regime      30%      IV percentile vs hist    Cheap IV → more hedge
  Momentum       20%      Recent equity returns    Drawdown → more hedge

  hedge_score = 0.50·tail_score + 0.30·iv_score + 0.20·mom_score  ∈ [0, 1]
  max_put_weight = hedge_floor + (max_opt - hedge_floor) · hedge_score

Tail score:  CVaR_eq from scenario distribution. Normalized:
             0 when CVaR ≤ 2%, 1 when CVaR ≥ 6% (was 4%; now less aggressive in mild regimes).

IV score:    Percentile of current IV vs. trailing window.
             1.0 when IV is at the bottom of its range (cheapest); 0 at top.

Momentum:    Sum of recent equity returns (lookback 5 periods).
             0.5 at neutral, 1.0 when cumulative return < -5%.

The hedge_floor (default 0.005 = 0.5%) ensures a small put position even in
calm markets — it's cheap insurance that prevents starting from zero when a
shock arrives.

Scenario CVaR mode additionally uses the **hedge_score** to impose a minimum
put floor when stress is high:
  - When `hedge_score >= 0.40`, enforce `min_put_weight ≈ 40% of max_put_weight`
    via a linear constraint in the CVaR optimizer.
  - In calm regimes (`hedge_score < 0.40`), no floor is imposed; the optimizer
    can choose zero puts if they are not justified by tail risk.


================================================================================
5. COMPARISON: WHEN TO USE WHICH
================================================================================

                        Markowitz++              Scenario CVaR
  ────────────────────  ───────────────────────  ───────────────────────
  Risk model            Gaussian (μ, Σ)          Full distribution (R)
  Tail sensitivity      None (2nd moment only)   Explicit (CVaR on tails)
  Options treatment     Delta-equiv Σ            Held-contract repricing
  Put spread support    Yes (via dynamic hedge)  Native (in scenario matrix)
  Dynamic IV            Via IEWMA + RND blend    Native (skew model in MC)
  Speed                 Fast (SOCP)              Fast (LP via R-U)
  Best for              Conservative allocation  Tail-risk-aware allocation
  Multi-asset           Not yet (single only)    Supported (3K+1 assets)

Switch mode in the notebook:
  MODE = "markowitz"  or  MODE = "scenario"

Or in code:
  config = ScenarioBacktestConfig(optimizer_mode="markowitz", ...)

6. DATA PIPELINE
================================================================================

  Source:     Alpaca Markets API (StockHistoricalDataClient, OptionHistoricalDataClient)
  Symbols:   SPY, AAPL, CRWD (extensible to any optionable equity)
  Storage:   data/raw/{symbol}_daily.parquet, data/raw/option_chains/{SYMBOL}/

  Fetch:
    python -m data.fetch_alpaca --symbols SPY AAPL CRWD
    python -m data.fetch_alpaca --symbols AAPL --no-historical  # bars + current chain only

  Chain layout:
    SPY:   data/raw/option_chains/calls_{date}.parquet (flat, backward compat)
    AAPL:  data/raw/option_chains/AAPL/calls_{date}.parquet
    CRWD:  data/raw/option_chains/CRWD/calls_{date}.parquet

  Multi-asset:
    Joint chain dates = intersection of dates where all symbols have data.
    Scenario matrix = column-stack of per-symbol (N, 3) blocks + one cash col.
